P1 — `scripts/uninstall.sh:364`, `scripts/uninstall.sh:370`, `scripts/uninstall.sh:373`, `scripts/uninstall.sh:376`  
A valid `--link` manifest record has the form `LINK  <relpath>  <target>`, but uninstall parses every record as `<sha>  <relpath>`. The resulting “relpath” contains both destination and target, so `_rel_unsafe` rejects it for containing a space. A repository installed with v1.3.0 `--link`, then upgraded to this candidate, cannot uninstall those deliveries: symlinks remain and the manifest is kept. The backup pass makes the same parsing error, so non-`.claude` link deliveries are also absent from the recovery archive. Minimal fix: parse LINK and hash records separately using the shared manifest grammar; unlink only when the current symlink target matches the recorded target, and add a v1.3 link-install → candidate-upgrade → uninstall/restore integration test.

The new security refusal path reports an “incomplete” uninstall but exits 0. P1 — `scripts/uninstall.sh:89`, `scripts/uninstall.sh:369`, `scripts/uninstall.sh:403`  
The script explicitly acknowledges that the manifest is not integrity-checked, yet treats every safe-looking record as proof of framework ownership. An injected record containing the current SHA of an adopter-authored in-tree file causes that file to be deleted without `--force`. The advertised `--no-hmac-verify` option only controls backup restoration; it does not verify the install manifest. Minimal fix: have install/upgrade produce an authenticated manifest sidecar and verify it before any backup, hashing, or removal; absence or mismatch must fail closed unless the operator explicitly supplies the bypass.

P1 — `scripts/uninstall.sh:318`, `scripts/uninstall.sh:340`, `scripts/uninstall.sh:350`  
The pre-uninstall archive and HMAC use predictable, second-resolution paths without destination confinement or exclusive creation. A pre-existing symlink or hard link named `.claude.backup-uninstall-<timestamp>.tar.gz`—or its `.hmac` sidecar—causes the write to follow or modify another inode, potentially outside the target. Minimal fix: create unpredictable files exclusively inside a physically validated target directory, refuse linked destinations, and atomically rename only after archive and HMAC generation succeed.
