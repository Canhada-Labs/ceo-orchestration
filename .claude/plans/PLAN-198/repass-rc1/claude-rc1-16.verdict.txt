NEW FINDINGS (annex)

P1 — .claude/hooks/_lib/bash_indirect_guard.py:156-178 (the result is returned through _scan at :492-493)
- Defect: the $( ) and <( ) matcher ignores quotes and only counts "$(" as an opening. The first ")" ends the substitution, even when that ")" is inside a quoted string. The truncated body is then scanned in strict mode. It usually has an unclosed quote, so shlex raises ValueError and the scan returns BLOCK bash_indirect_unparseable_shell.
- Scenario, on by default for every adopter. Each of these legitimate commands is blocked:
  - echo $(python3 -c "import sys; print(sys.version)")
  - VERSION=$(node -p "require('./package.json').version")
  - git log -1 --format with a quoted format containing parentheses, inside $( )
  - $(jq '.items | map(.id)' f)
  - $(awk '{print substr($1,1,3)}' f)
  - diff <(jq -S '.a | map(.b)' x) y
- The block names "indirect shell execution". CEO_BASH_INDIRECT_HEURISTICS=0 does not help; only CEO_BASH_INDIRECT_GUARD=0, set before Claude Code starts, does.
- The legitimate-allow corpus in tests/test_check_bash_safety_indirect_exec.py:66-82 has no $( ) case with a parenthesis inside quotes.
- Minimal fix:
  - In the inner cursor loop, track single and double quotes and backslash escapes.
  - Count a bare "(" as an opening outside quotes.
  - If no balanced ")" is found, leave the command to the existing guards instead of blocking in strict mode.
  - Add the cases above to the allow corpus.

P2 FOLLOW-UPS

1. Here-doc consumer misattributed (bash_indirect_guard.py:224-235). The consumer is the first word of the whole prefix since the last here-doc, not the command that actually reads the here-doc.
   - False positive: bash scripts/test.sh && git commit -m "$(cat <<'EOF' / Don't break it / EOF)". The commit message is parsed as shell, the apostrophe leaves an unclosed quote, and the command is blocked as unparseable. The same happens for any command that starts with sh, bash, zsh, dash, ksh or eval and later passes a here-doc to a data tool.
   - False negative: cd x && bash <<'EOF' and sudo bash <<EOF are never scanned.
   - Fix: take the consumer from the segment that holds the << operator, after _normalise.

2. Comment handling treats { and } as word boundaries (_prelex at bash_indirect_guard.py:96). In bash, braces are not metacharacters, so # after them does not start a comment.
   - Scenario: echo $(( ${#arr[@]} - 1 )), or a backtick or $( ) containing ${#x}. The rest of the line is stripped as a comment, the $( has no closing parenthesis, and the command is blocked as unparseable.
   - Fix: drop "{}" from the boundary set.

3. Whole-command size limit (bash_indirect_guard.py:19 MAX_BODY_BYTES=16384, checked in _scan at :472-473). Any Bash command over 16,384 characters is blocked, including a plain here-doc file write.
   - The CHANGELOG declares a size limit but gives no number. Its adopter notes mention only indirect forms and unparseable bodies.
   - The block reason says "indirect shell execution".
   - The module docstring (lines 1-6) says unrecognised input is left to the existing guards, which is not true for the limits or strict mode.
   - Fix: give the number in the docs, word the reason per code, and correct the docstring.

4. Interpreter operands treated as write targets (bash_indirect_guard.py:455-461). An operand after python, node, ruby or perl -c/-e is checked as a canonical write target with no evidence of a write.
   - Read-only commands are blocked as bash_computed_canonical_target, for example python3 -c "import ast,sys; ast.parse(open(sys.argv[1]).read())" .claude/hooks/x.py.
   - Python's -E (ignore environment) is also treated as an eval flag.
   - Fix: limit this to -c/-e/--eval for each interpreter and require a write signal.

5. Brace expansion applied to quoted words (bash_indirect_guard.py:322-345, :364-371). Bash does not brace-expand inside quotes. A JSON, jq or Python-dict argument with more than 128 comma items, or two arguments whose counts multiply past 128, is blocked as bash_indirect_limit.
