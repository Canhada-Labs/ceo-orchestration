NEW FINDINGS (annex)

P1-1. Common valid commands are blocked as "unparseable"
- Where: bash_indirect_guard.py:159-171.
- Cause: the code that finds the end of a $(...) or <(...) body ignores quotes and plain "(". The first ")" ends the body.
- Trace: V=$(python3 -c "print(1)") gives the body: python3 -c "print(1. Strict _words then raises "No closing quotation", and lines 489-493 return bash_indirect_unparseable_shell. posture_scan.py:582 tags that block destructive=True.
- Other blocked examples: echo "$(node -p "require('./package.json').version")" and n=$(jq '[.[]|select(.ok)]|length' f.json).
- The block is not tied to the heuristics switch, so only CEO_BASH_INDIRECT_GUARD=0 avoids it. The allow tests (test_check_bash_safety_indirect_exec.py:66-82) have no such case.
- Adopter impact: routine read-only one-liners get blocked in upgraded sessions. Each block can be worked around by rewriting the command. The session is not stopped.
- Minimal fix: inside the body scan, skip quoted spans and count unquoted "(" as nesting (bash's own matching rule). Add the three examples as allow tests.

P1-2. The scan's limits let commands through, against CHANGELOG [1.4.4] lines 93-94 ("fails closed ... at its depth, size and word limits")
- (a) Where: bash_indirect_guard.py:386-399. _scan_segment recurses into xargs/find bodies with depth+1 but never checks MAX_DEPTH. Example: echo ~ | xargs xargs ... xargs rm -rf, with about 1000 xargs. That stays under MAX_WORDS (1024) and is about 6 KB, under MAX_BODY_BYTES. The recursion raises RecursionError, decisions_cli.py:243 catches it, and the hook ALLOWS. The repo's own doctrine (posture_parser.py:369) calls a RecursionError inside a security matcher a fail-open.
- (b) Where: bash_indirect_guard.py:243. _normalise strips at most 12 launchers, then returns a launcher as the command word. "command" repeated 13 times, then rm -rf ~, passes this scan. It also passes the base _check_rm_rf, because normalization.py:103 does not strip command or nohup. A single "command rm -rf ~" is blocked.
- Neither case is a regression against v1.4.3-rc.1, where both commands were already allowed.
- Minimal fix: return _hit("bash_indirect_limit") when depth > MAX_DEPTH at the top of _scan_segment, and when _normalise uses all 12 passes and still has a launcher as head. Catch RecursionError in scan() and return the same limit hit.

P1-3. Two parsing defects let a simple prefix skip the scan
Both contradict CHANGELOG line 84 ("inside sh -c, eval or a here-doc"). Neither is a regression against the base.
- (a) Where: bash_indirect_guard.py:95-96. Comment stripping treats "{", "}" and ")" as the start of a new word. So the "#" in ${#var}, ${x}# or $(cmd)# is read as a comment, and the rest of the line is dropped before both _command_substitutions (line 144) and _words (line 101). Example: n=${#list}; sh -c 'rm -rf ~'. The scan sees only "n=${" and ALLOWS. The base guard also allows it, because the command word is sh.
- (b) Where: bash_indirect_guard.py:224-227. The heredoc "consumer" is taken as the first word of all text since the start or the previous heredoc, not the command that owns the "<<". So true && bash <<'EOF' (body rm -rf ~), FOO=1 bash <<EOF, sudo sh <<EOF and cd x; bash <<EOF never have their body scanned. The opaque-stdin check (line ~523) looks for "<" in the token list, not "<<", so these commands are ALLOWED.
- Minimal fix: treat "{" and "}" as part of a word, and a ")" that closes "$(" as part of a word. Take the heredoc consumer from the last simple command in the prefix, after _normalise. Treat "<<" like "<" in the opaque-stdin check. Add tests for both.

- P2-1. False positives of the heuristic forms (switch-gated; condition 6 says false-positive limits were never measured):

  - Line ~523 blocks bash ./x.sh < /dev/null as opaque stdin.

- P2-2. Glob false positive at bash_indirect_guard.py:431-435. fnmatch's "*" crosses "/", so fnmatchcase(".claude/settings.json", "*.json") is True.
