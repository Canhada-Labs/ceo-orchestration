Failure scenario: _scan_segment (bash_indirect_guard.py:347) recurses once per xargs level with no depth check; MAX_DEPTH is enforced only in _scan (:472). A command `xargs xargs ...(about 1000 times) rm -rf ~` stays under MAX_WORDS=1024 and MAX_BODY_BYTES=16384. The legacy matchers never see `rm` (tokens[0] is xargs; _e3 and _e4 walk iteratively without hitting it). The new scan then raises RecursionError at the default limit of 1000. decide_command does not catch it, and main()'s `except Exception` emits allow with a FATAL line on stderr, so GNU xargs runs rm -rf ~. This is fail-OPEN on input a security matcher cannot handle (item 2). The repo's own doctrine calls this out: posture_parser.py:369 says a RecursionError in a security matcher is a crash, i.e. a fail-open. It also contradicts CHANGELOG.md:93-94 ("fails closed ... at its depth, size and word limits"). It is not a regression vs the base, which never blocked xargs-wrapped rm -rf at all, and it needs a deliberately built ~1000-token command, so it is not P0.
Minimal fix: add `if depth > MAX_DEPTH: return _hit("bash_indirect_limit")` at the top of _scan_segment. Optionally, at posture_scan.py:578, map a RecursionError from scan() to a bash_indirect_limit block while keeping ImportError fail-open. Add a regression test with ~1000 nested xargs.
