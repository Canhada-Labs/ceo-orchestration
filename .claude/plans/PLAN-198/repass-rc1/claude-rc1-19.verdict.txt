NEW FINDINGS (annex)

P1 — In a hook-only session nothing drains the audit spool. Spool-routed audit events stay out of the HMAC-chained log indefinitely, and condition 8 and the CHANGELOG do not say so.
FILE:LINE: .claude/hooks/_python-hook.sh:410; .claude/hooks/_lib/_spool_writer_parts/lifecycle.py:346-358 and :361-375; .claude/hooks/_lib/_audit_emit_parts/writer.py:579-592; .claude/hooks/_lib/_spool_writer_parts/prepare.py:83-122; CHANGELOG.md:129-132 and :402-405.
Failure scenario:
- Every hook registered in .claude/settings.json runs through _python-hook.sh, so every hook process now skips leg 2 (the forced drain at exit).
- Leg 1 (the in-life opportunistic drain) is effectively unreachable in a hook. should_drain() runs right after spool_append has just refreshed the process's own spool mtime, so the >100 ms age trigger cannot fire. The only reachable trigger is 100 body lines in the process's own spool, which a short hook does not produce. PLAN-194 LEDGER:178 records the same finding.
- The only remaining drainers are non-hook processes that import audit_emit (for example /ceo-boot run through Bash). Each exit runs one drain_now(force=True), which moves at most K_MAX=100 entries (drain.py:200-203).
- ADR-055-AMEND-4 §4.2 (lines 169-171) says the required unbounded drain caller at boot or nightly is "não está integrado".
- Result for an upgrading or fresh adopter:
  (a) Every audit_emit event (blocks, VETOs, canonical-edit decisions, telemetry) accumulates in per-PID spool files that have no HMAC. No reader merges the spool: /ceo-boot 24h windows, audit-query, check_tier_policy_misrouting_24h and the Stop/SessionEnd summaries all read only audit-log.jsonl.
  (b) Each later drain re-reads and re-parses the whole backlog and rewrites every spool file it did not fully consume (drain.py:489-556), with an fsync each, while holding the canonical lock. So drain cost grows with the backlog. A long hold can push audit_log.append_entry past its 2.5 s lock timeout and drop agent_spawn rows ("would-log"), the rows check_budget sums. That direction fails open.
  (c) The journal buffer is no longer flushed at exit, and it only flushes every 10 envelopes, i.e. 5 events (writer.py:294-297). So a hook with four events or fewer never writes begin/commit envelopes to disk. check-audit-real-loss.py G6 (:7-19, :125-144), the ADR's active real-loss revert trigger, then cannot see those records at all.
- No governance hook is disabled, no session is blocked, and events are fsync'd. That is why this is P1, not P0.
- The CHANGELOG line "its events wait in the spool for a later drain, so they can reach the log later" implies a scheduled drain that does not exist for hook-only sessions.
Minimal fix: either land the ADR §4.2 unbounded drain caller outside hooks (for example a drain-to-fixed-point step in /ceo-boot or a nightly job, with a budget), or declare in condition 8 and Known-open that:
- hook processes never drain;
- non-hook audit_emit importers drain at most 100 entries per exit;
- the canonical log and the G6 meter lag accordingly.
Optionally, flush the process's own journal buffer at bounded exit with FileLock timeout=0, so G6 keeps seeing commits.

P2 FOLLOW-UPS
1. The exit_deadline_skip breadcrumb gets written on every exit of every hook that imports audit_emit, even when nothing is pending.
   - Where: lifecycle.py:348-349 and spool_writer.py:531-532. install_exit_handlers runs when audit_emit is imported (audit_emit.py:494); policy.py, scratchpad_lib, otel_emit and _bash_safety_parts/normalization.py all import it.
   - Effect: audit-log.errors grows about one line per hook invocation, with no bound. /ceo-boot check_audit_log_freshness (_ceo_boot_parts/state_plan_audit.py:459-483) and ceo-diagnose.py:364-422 read any non-empty file as write failures (yellow), and status.py:290 warns above 20 lines. Those signals become permanently yellow, which masks the FAIL-CLOSED flood detector (F-6.3).
