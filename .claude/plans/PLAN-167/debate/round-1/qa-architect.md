## Summary (≤ 3 bullets)

- The core thesis is sound: the table-plus-pure-function architecture is the correct cure for a patch-loop where "correct" was decided one branch at a time. The masking finding (§5.7) is the most structurally important result — it reveals that three surface-guard rows have been asserting a path no end-to-end run could reach, and that this class generalises to every tree-walking reader in the upgrade pipeline.
- Two deliberate inconsistencies cannot both survive W2: `OWN-0018` vs `OWN-0020` have identical nine-dimension keys and opposite verdicts, and `OMIT_RECORD` vs `PRESERVE_UNOWNED` have overlapping domain but different operator semantics. The function cannot be written until these are resolved; the debate must decide, not defer.
- OQ-7 (`fault=` as a prose-encoded tenth axis) is a blocking gap the document itself flags as "the one option that should not survive." The harness parses only one fault value (`backup_unwritable`, `test-ownership-table.sh:516`); a second fault type added to `note` without a matching harness case silently skips injection and the row may GREEN for the wrong reason.

## Risks

- **R-QA1** — SEVERITY: HIGH. `fault=` is an unvalidated tenth dimension encoded in the `note` column. The harness has exactly one case (`*fault=backup_unwritable*`, line 516). Adding any new `fault=<x>` to the TSV without a matching harness case silently produces no injection. The row then runs without the injected condition and may match its expected verdict by coincidence, producing a vacuous GREEN. Evidence: grep on the harness shows no dispatch table and no validation that all `fault=` values in the TSV have corresponding harness support. This is the generalisation of fixture defect #3 (symlink silently left pointing somewhere else) that the plan warns about in §9.

- **R-QA2** — SEVERITY: HIGH. The three TIMEOUT rows (`OWN-0025`, `OWN-0029`, `OWN-0033`) expect verdicts that their surface guards are supposed to produce (`ABORT_SURFACE/HASH_PRIOR_RECORD`, `PRESERVE_UNOWNED/HASH_NONE`, `PRESERVE_UNOWNED/HASH_NONE` respectively). Verified: all three time out at rc=137 (`test-ownership-table.sh --only OWN-0025,OWN-0029,OWN-0033 --keep` output). When W2 fixes the scanner, these rows must not only stop timing out — they must reach the correct SURFACE guard. The harness has no mechanism to distinguish "scanner no longer blocks, surface guard fires correctly" from "scanner no longer blocks, some other pre-guard aborts first." Without a standalone scanner test (FIFO at surface path → scan exits 0), a scanner fix that merely moves the hang point is indistinguishable from a complete fix. These rows will turn GREEN but the guards they claim to test may still be unreachable.

- **R-QA3** — SEVERITY: HIGH. `OWN-0018` and `OWN-0020` have nine-dimension keys that are byte-identical (`spec / none / dir / legacy_pristine / yes / copy / maintainer / upgrade / none`) but produce opposite verdicts (`REFRESH/HASH_SOURCE` vs `PRESERVE_UNOWNED/HASH_NONE`). The table currently resolves the distinction via prose in `note` (`extra=adopter_symlink`). A pure function that takes the nine declared dimensions as parameters cannot produce two different outputs for the same input. This is not a design-coherence issue; it is a mathematical precondition for W2. Verification: `awk -F'\t' 'NR>1{key=$2" "$3" "$4" "$5" "$6" "$7" "$8" "$9" "$10; seen[key]++; id[key]=id[key]" "$1; verd[key]=verd[key]" "$11} END{for(k in seen) if(seen[k]>1) print k, "→ IDs:", id[k], "verdicts:", verd[k]}' ownership_table.tsv` produces: `spec none dir legacy_pristine yes copy maintainer upgrade none → IDs: OWN-0018 OWN-0020 verdicts: REFRESH PRESERVE_UNOWNED`. The proposed solution (`legacy_pristine_partial` as a new `live_content` value) is structurally correct but has not been ratified; the debate must decide it.

- **R-QA4** — SEVERITY: MEDIUM. R-10 (equivalence classes) declares that for a cell where `mode=*`, the outcome does not depend on mode. The harness instantiates the `*` by picking `copy` implicitly (`base_mode` defaults to `copy` unless `prior_record` forces `link`, line 470). This is undocumented. If the production code branches on `mode` in a dimension the table claims is `*`, the harness would test only the `copy` representative and pass. The one confirmed case where this matters: `OWN-0030/0031` (ancestor_symlink rows) mark `live_content=*`. The model claims content is irrelevant there because the function short-circuits on ancestor. If the production code does not short-circuit correctly and the content branch is reached, the test would not catch it, because the harness never exercises a non-`*` representative for that row.

- **R-QA5** — SEVERITY: MEDIUM. `_derive_verdict` reads `_MTIME_BEFORE`/`_MTIME_AFTER` as globals (lines 399, 525, 565). These are set per-row in `_run_row`. If `_derive_verdict` is ever called outside `_run_row` (e.g., from a unit test or a future harness refactor), it reads stale values from the previous row without any indication of error. This is an implicit contract that is one extraction away from producing wrong verdicts silently.

- **R-QA6** — SEVERITY: MEDIUM. Three protocol surface rows lack coverage for `prior_record=none` with hostile `live_type`. The table has `OWN-0032` (`protocol + hash + dir + upgrade`) and `OWN-0034` (`protocol + hash + symlink + upgrade`) but no row for `prior_record=none` with the same live types. On upgrade with `prior_record=none`, ownership logic takes a different branch (the framework treats it as unowned and skips the refresh). The skip path for `live_type=dir` on `protocol` is untested: `cat > $TARGET/PROTOCOL.md` fails with "Is a directory" under `set -euo pipefail` if the guard does not fire first. The model claims the table covers these via R-10 equivalence on `prior_record`, but `prior_record=none` is not `*` — it is an explicitly enumerated dimension value, and the branch it takes in the ownership check is structurally different from `prior_record=hash`.

- **R-QA7** — SEVERITY: LOW. `_ABORT_MARKERS='REFUSING to|could not back up|unsupported special file|backup-before-replace'` (line 182) couples the harness to specific output wording. This is a deliberate choice documented in §5.6. However, a debug or warning message that incidentally uses "could not back up" on a PRESERVE path (e.g., a pre-existing non-fatal log) would cause `_derive_verdict` to report ABORT_SURFACE when the content was unchanged and no ABORT_SURFACE intent existed. The current scripts do not have such messages (verified by grep), but this is a fragile coupling.

## Must-fix (blocking)

1. **OQ-7 must close before W2.** The document's own §6 states that leaving `fault=` in free text is "the one option that should not survive." This debate must produce a decision: either (a) add a 15th column `fault` to the TSV schema and update the harness to validate that every non-empty `fault` value has a case, or (b) explicitly rule the `fault=backup_unwritable` rows out of scope, mark them `skip=reason` in the TSV, and document that backup-failure behaviour is verified by a separate dedicated test. Option (b) is the lower-friction path and does not weaken coverage if a dedicated test exists. Neither option is worse than the current state; the current state is the worst. **Actionable as a table change**: either add the column header or add a `skip=` annotation. The function signature is not affected.

2. **OWN-0018 vs OWN-0020 must be resolved before W2.** The function cannot return two different outputs for the same nine-tuple. The `extra=adopter_symlink` in `note` is a tenth observable that is not a dimension. The proposal's `legacy_pristine_partial` value for `live_content` is structurally correct: it names a distinct observable (a tree carrying an entry the fingerprint cannot fully inventory) that genuinely separates the two rows. **This debate must either ratify `legacy_pristine_partial` as a valid `live_content` value (adding a row to the TSV and a new `legacy_pristine_partial` path to `_mutate_surface`) or propose an alternative column.** Without this decision, W2 has no specification to implement against.

3. **TIMEOUT rows need a staged verification protocol.** The W2 task that fixes the scanner (§5.7, `_emit_deprecation_warnings`) must be paired with an explicit positive control: a standalone invocation of the scanner subsystem alone, given a target tree containing a FIFO at the `SPEC/v1` path, that exits 0. This control must be documented in the W2 execution record and must precede the green count of the three TIMEOUT rows as evidence. Without it, a scanner "fix" that moves the blocking point (e.g., a second reader further downstream) would make the three rows GREEN without testing the guards they claim to cover. **Actionable as a plan amendment to §W2**: add a step "W2.0 — scanner positive control: `test-ownership-table.sh --only OWN-0025` preceded by a standalone scanner probe that confirms non-blocking exit". This does not change the table or the function signature.

If the model's equivalence claim for `mode` is ever wrong, the failure would be immediately attributable rather than silent.

2. **`ancestor_symlink` + `install_rerun` coverage.** `OWN-0030/0031` cover `ancestor_symlink` for `operation=upgrade` only. `install_rerun` with an ancestor symlink is a legal cell under the legality rules (no rule prunes it), and the ownership check on `install_rerun` takes a different branch than `upgrade`. Two rows (`spec + hash + ancestor_symlink + install_rerun` and `marker + hash + ancestor_symlink + install_rerun`) are absent. The expected verdict is likely `OMIT_RECORD/HASH_NONE` for the same reason as the upgrade rows (§5.8: dead-branch, relpath sanitizer drops the record before the continuity check runs). If correct, these rows are quick GREEN confirmations; if wrong, they are the next open finding.

3. **Harness self-test (negative control).** The plan documents five fixture defects; the fourth (vacuous GREEN on `link_match` rows) was found only because the harness was inspected, not because a failing test caught it. A single negative-control test that deliberately misconfigures one well-understood fixture and verifies the harness returns RED would serve as a regression guard for future fixture additions. Example: remove the `link_match` guard at `_mutate_surface:274` and verify that at least one `link_match` row goes RED.

4. **`protocol` + `prior_record=none` + hostile `live_type` (R-QA6 follow-through).** Three rows: `protocol + none + dir + upgrade`, `protocol + none + special + upgrade`, `protocol + none + symlink + upgrade`. ## Unseen by the original plan

1. **C1 (OMIT_RECORD reduction) loses the operator transition signal.** The claim is that every `OMIT_RECORD` row would read `PRESERVE_UNOWNED` if `prior_record=none`, so `OMIT_RECORD` is redundant. This is mechanically true for the filesystem outcome — neither verdict writes anything. But it erases a distinct operator signal: `OMIT_RECORD` says "I found a prior record and dropped it"; `PRESERVE_UNOWNED` says "there was never a record." The operator's next action differs. For `OWN-0028` (marker + prior hash + dir → OMIT_RECORD), the operator learning they had a marker record that was silently dropped should investigate differently from learning there was never a record. The plan's own argument for keeping `ABORT_SURFACE` separate from `PRESERVE_UNOWNED` (§3.1: "the operator must be told") applies with equal force here. C1 is architecturally clean but operationally lossy. A weaker form — "collapse OMIT_RECORD to PRESERVE_UNOWNED only in the dead-branch rows (OWN-0030/0031) where the record drop is a sanitizer artifact, not a framework decision" — would preserve the signal on the rows where it is meaningful.

2. **OWN-0024 and OWN-0027 are RED for a reason the plan does not address.** Running `test-ownership-table.sh --only OWN-0024,OWN-0027` produces `got=PRESERVE_OWNED/HASH_PRIOR_RECORD` for both, not `ABORT_SURFACE`. The `fault=backup_unwritable` injection makes `.claude.bak` unwritable (chmod 500, line 516-518). The scripts do emit the ABORT markers on the backup-failure path (upgrade.sh lines 1954-1955, 2059-2060), and the harness redirects stderr to `$out`. The RED result means the backup-failure path is not being reached — either the backup attempts a different directory, or the chmod 500 on `.claude.bak` does not prevent the actual backup path the scripts use. This is a fixture defect, not a subject defect: the fault injection is not injecting the fault. The plan does not document this specific RED cause, and it is distinct from the four documented fixture defects. It should be verified before W2 treats these rows as "code to fix" rather than "fixture to fix."

3. **INV-1 and INV-2 are cross-row invariants with no regression guard.** The harness asserts them "across every applicable row" (§5.5), but inspecting the harness source, there is no code that implements INV-1 or INV-2 assertions. The `_run_row` function captures before/after state for a single surface per row. INV-1 requires verifying that paths OUTSIDE the continuity set did not change their recorded digest — but the harness only reads the record for `$rel` (the surface under test). INV-2 requires verifying that no new LINK records appear for paths that were not already LINK records — but again, the harness only checks `_obs_record` for the surface under test. These invariants are declared but not implemented in the current harness. If they were to be implemented, `_run_row` would need to snapshot the entire manifest before and after, not just the one surface's record.

## What I would NOT change

1. **R-10 (equivalence classes).** The alternative — full enumeration at 24,000 rows with a 60-second cell timeout — produces an 1,600-hour suite that cannot be run. Equivalence classes with explicit `*` notation and stated representatives are the only practical path. The risk (R-QA4 above) is manageable by documentation; eliminating R-10 is not.

2. **The mtime-on-upgrade-only restriction (lines 399-401).** The plan earned this restriction by finding that install.sh re-runs placeholder substitution on every invocation (fresh mtime, identical bytes). Relaxing the restriction to include the install path would resurrect a false-REFRESH class that costs nothing to avoid. The stated boundary ("Restricted to upgrade deliberately") is correct and must not be widened without a new finding.

3. **The `_next_source` perturbation discipline.** Differentiating the source used for upgrade from the one used for the install base is what separated `HASH_SOURCE` from `HASH_PRIOR_RECORD` across 40 rows that previously read as ambiguous. This is the single most important fixture correctness mechanism in the harness. The perturbation (appending a marker to the first SPEC/v1 file and writing `1.3.1` to the marker) is minimal and targeted; it is not gaming the test.

4. **The two-oracle architecture (unit for the decision function, e2e for caller observability).** This is the structural cure for the 40-minute-per-cell loop. The unit oracle catches wrong decisions in milliseconds; the e2e oracle (the current harness) catches correct decisions being executed incorrectly. They are not redundant — they fail for different reasons. Collapsing them back into one slow oracle is how S296's loop is recreated.

5. **The `indistinguishable=` annotation and AMBIG status.** The 2024-style approach of silently preferring one hash candidate over another when they are byte-equal was the root cause of fixture defect #1. Marking those cells explicitly AMBIG and requiring fixture differentiation before claiming them GREEN is the correct discipline. It should not be weakened by adding a tie-breaking preference rule.
