## The activation step that was executed

The installer delivers the CI file INERT, as
`.github/workflows/validate.yml.template`; GitHub Actions never reads a
`.template` file. Activation is one explicit adopter move, content
untouched:

```bash
mv -n .github/workflows/validate.yml.template \
      .github/workflows/validate.yml
```

`mv -n`, not `git mv`: on a fresh install the delivered file is UNTRACKED, so
`git mv` fails (rail 183-r1), and `-n` refuses to clobber a `validate.yml` the
adopter already has (rail 183-r3). After the rename, `cmp` against
`templates/.github/workflows/validate.yml.template` reported no difference: the
activated file is byte-identical to what the installer delivered.

## What these runs prove, and what they do not

They prove what AC-2 asks: the delivered template, activated by the named
step, ran on real GitHub Actions in a disposable repository of ours and came
out green. They also cover what the in-repo emulator cannot: `shellcheck`
pre-installed on `ubuntu-latest`, `actionlint v1.7.7` downloaded by the step
itself, and the SHA-pinned `Checkout` action actually executing.

They do NOT bind these runs to the shipped template BYTES from committed
state alone. The captured object carries workflow name, step names, statuses
and timestamps — not the workflow blob, the `run:` bodies, the action
references or the installer output. A workflow keeping the same names could
produce an equivalent object, so an offline reviewer gets NAME-level
agreement (the eleven step names below do match the template at `bc52016`),
not a cryptographic binding. The `cmp` against
`templates/.github/workflows/validate.yml.template` reported byte-identity at
capture time and is recorded here as a statement of the session that ran it,
not as re-checkable evidence. Closing AC-2 on this artifact therefore rests
on the Owner's written criterion (`PLAN-183/owner-decisions-S344.md`), not on
byte-level reproduction. Raised by the S344 land rail; recorded, not cured.

They do NOT establish that the rename ALONE arms the scheduler. The first
three pushes produced no run at all over roughly 18 minutes with the workflow
registered and Actions enabled; runs began on the fourth push, which also
carried a re-PUT of the `actions/permissions` setting and a second workflow.
Cause not attributed. That question stays open, recorded here.
