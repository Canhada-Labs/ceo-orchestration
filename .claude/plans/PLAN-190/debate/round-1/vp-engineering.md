## Summary

- **O que a W1 tenta:** registrar cada chamada da tool `Workflow` ANTES do despacho (sha256 do script, `args` literal, `resumeFromRunId`, revisão do código), vincular o `wf_<id>` no PostToolUse e BLOQUEAR uma retomada cujo script ou `args` difiram do manifesto vinculado — a classe medida (17 fatias reimplementadas por edição de prompt; 11 regressões por args de memória).
- **Onde é forte:** o registro pré-despacho no hook (não no script do consumidor) é a decisão certa; `args` literal canônico com ausente ≠ `null` ≠ `{}` é exatamente o predicado que a chave de cache do runner exige («same script + same args → 100 % cache hit», skill `workflow-authoring` §Resume); fail-open de infraestrutura, kill-switch, derivador idempotente que reproduz o patch byte a byte sobre HEAD limpo (medido: 3 arquivos IDENTICAL), hygiene de teste limpa, contagens sem drift, `build-plugin --check` verde.
- **Onde é fraco:** (1) a tool `Workflow` é SÍNCRONA — o `runId` só chega no retorno, logo a morte de processo/reboot (a metade do incidente que motiva o plano) NUNCA vincula o manifesto e o guard fica `no_manifest`/advisory exatamente quando importa; (2) o guard bloqueia por hash de arquivo inteiro um caminho DOCUMENTADO do harness («resume after a pause, kill, or script edit — the longest unchanged prefix … returns cached results»), com uma rota de override (`CEO_WORKFLOW_RESUME_FORCE=1`) que é variável de ambiente do processo da CLI — o modelo em execução autônoma não consegue ligá-la; (3) a suíte existente fica VERMELHA (`test_template_dogfood_parity.py::test_registration_counts`: `52 != 50`, pino ratificado) — «23 verdes» vale para os testes novos, não para o corpus.

## Risks

1. **R-VP1 — CRITICAL — o canal de vínculo é cego à classe de morte.** A skill `workflow-authoring` afirma: «The tool result includes a runId» e «Before diagnosing why a *completed* workflow returned…» — a tool devolve quando o run TERMINA (completo, pause, kill, agente morto por quota devolve `null` e o script segue). Morte do processo/reboot/`Ctrl-C` ⇒ sem PostToolUse ⇒ `decide_post` (`launch_ledger.py:377-390`) nunca corre ⇒ `find_launch_for_run` devolve `None` ⇒ `guard.result = no_manifest` ⇒ ALLOW. O contrato do hook o admite («No bound manifest … ⇒ advisory», `check_workflow_launch.py:18-19`), mas a proposta vende «a W1 fecha essa classe». *Mitigação:* vincular pelo artefato que o HARNESS já escreve no lançamento — `<session>/workflows/scripts/<meta.name>-wf_<hex8>-<hex>.js` (medido neste repo: 123 scripts persistidos, 91 nesse padrão; referência em `.claude/plans/PLAN-186/w0/us4-inherit-vs-pin-S340.md:73`) — por CONTEÚDO (sha256 do arquivo == `manifest.script.sha256`) no PostToolUse e, na PreToolUse de uma retomada sem manifesto vinculado, por glob do run id sobre as sessões do projeto. Independe da forma da resposta e cobre o run morto.
2. **R-VP2 — HIGH — bloqueio por padrão sobre um caminho de iteração documentado.** Edição do script + `resumeFromRunId` com prefixo cacheado é o fluxo que a própria skill recomenda («To iterate on a workflow, edit that file … re-invoke Workflow with `{scriptPath}`»). O predicado `script.sha256` (`launch_ledger.py:337`) não distingue «mudou o prompt das fases concluídas» (a perda) de «corrigi a fase 4» (o uso legítimo). Enforce ⇒ falso bloqueio em toda iteração ⇒ o operador aprende a forçar ⇒ canal treinado para ser ignorado. O plano se contradiz: W1 diz «divergência ⇒ bloqueia» (`PLAN-190…md:107`), «How to continue» manda «medir por 2 semanas antes de qualquer flip para enforce» (:216-217) e a regra de parada fala em «janela advisory» do guard de W1 (:232-233). *Mitigação:* dividir o guard — `args` divergentes BLOQUEIAM (não há caso legítimo: mesma corrida, entradas diferentes); script divergente é ADVISORY nomeado (`mismatch_script_advisory`, aviso ruidoso com a rota `relaunch`), com flip por cerimônia após a janela medida por `report`.
3. **R-VP3 — HIGH — a rota de override não existe dentro da sessão.** `decide_pre` lê `env.get("CEO_WORKFLOW_RESUME_FORCE")` (`launch_ledger.py:368`) e o motivo manda «set CEO_WORKFLOW_RESUME_FORCE=1» (`:349`). Hooks herdam o ambiente do processo da CLI; o modelo não exporta variáveis para eles e não pode editar `settings.json` (canônico + `check_config_change`). A população-alvo do plano (execução autônoma) fica presa: só o operador humano reiniciando a CLI destrava. O precedente do repo é rota por ARQUIVO (`<projeto>/.claude/turbo-off`, `settings.user.json._derivation.blocking_inclusions`). *Mitigação:* token one-shot por run, `ceo-launches.py force <run_id> --reason "…"`, consumido e registrado como `mismatch_forced` com o motivo; a env var pode ficar como rota do operador.
4. **R-VP4 — MEDIUM — o hook paga antes de registrar.** `build_manifest` chama `git_revision(cwd)` (`launch_ledger.py:221`) com `rev-parse` timeout 3 s + `status --porcelain` timeout 5 s (`:168`, `:171`) ANTES de `write_manifest` (`:373`); a registração dá `"timeout": 5` (`.claude/settings.json:362-368`). Num consumidor grande com cache frio, o hook estoura o orçamento: fail-open E nenhum manifesto — o AC «100 % dos lançamentos com manifesto» morre em silêncio. *Mitigação:* escrever o manifesto primeiro e enriquecer `code` depois; `git status --porcelain --untracked-files=no` com timeout 1 s; registração com timeout 10.

## Unseen

1. **A tool é síncrona.** Nada no plano ou na proposta diz quando o PostToolUse dispara; o desenho inteiro do vínculo assume «no lançamento» e o harness entrega «no retorno». O caso que motivou o plano (morte a meio do run) é o único em que o vínculo por resposta não acontece.
2. **O harness já mantém um registro de lançamento do script** (`workflows/scripts/<name>-wf_<id>-<hex>.js`, escrito na invocação, com o run id no nome). A W1 re-deriva a metade fraca (hash) e ignora a forte (texto + id + path). Consumir esse artefato torna o guard aplicável a runs anteriores ao ledger.
3. **Edição + retomada é funcionalidade, não acidente.** O predicado certo para a perda é «mudou o prompt de um `agent()` já concluído», que só o `journal.jsonl` do run conhece (`started`/`result` por chave `v2:<hash>`); o hash do arquivo é proxy grosseiro — por isso advisory + medição, não enforce.
4. **Override por env var não é rota para o modelo.** A população-alvo é autônoma; toda rota de recuperação tem de ser executável por quem lê o motivo do bloqueio.
5. **Fronteira por slug de projeto.** O ledger resolve por path (`runtime_paths`, ADR-001); uma retomada emitida de uma sessão em worktree resolve OUTRO state dir ⇒ `no_manifest` ⇒ advisory silencioso. Declarar no doc; `--project-dir` cobre a consulta manual.
6. **Pinos ratificados e contrato de derivação** (`T64_*`, `blocking_inclusions`) — a classe «EXPECTED declarado à mão envelhece» já registrada em memória do repo.

## What I would NOT change

- **Registrar ANTES do despacho, no hook.** O script do consumidor não vê a chamada; o hook vê `tool_input` inteiro. Correto e independente do ciclo de vida do harness.
- **`args` literal canônico, ausente ≠ `null` ≠ `{}`, comparação por chave de topo com hashes.** É o predicado que o cache do runner usa (determinismo imposto: `Date.now()`/`Math.random()` proibidos nos scripts) e a granularidade certa para o operador corrigir.
- **Bloquear `args` divergentes.** Não existe caso legítimo de «mesma corrida, entradas diferentes»: é o incidente das 11 regressões.
- **OQ-3: `code.head` só registrado.** Retomar sobre WIP commitado é legítimo; invalidação por revisão pertence ao checkpoint da W2. Comparar aqui seria um segundo falso-bloqueio.
- **Fail-open de infraestrutura + kill-switch + «não é matcher de segurança».** Coerente com CLAUDE.md §4; o guard é instrumento de recuperação.
- **Derivador como fonte única das registrações** (3.ª lane medida: `settings.json`, `settings.base.json`, `settings.user.json` IDÊNTICOS ao patch; `--check` idempotente rc 0; `gen-settings-user-template --check` OK).
- **Hook no perfil `user`** (OQ-3 do plano): é proteção do operador — desde que a rota do item 3 exista.
- **Nenhum evento de auditoria nesta wave** — disciplina de escopo correta, desde que o follow-up seja nomeado.
- **Forma dos testes:** e2e em subprocesso pelo mesmo caminho do shim + unit sobre a lib, `TestEnvContext` (gate de hygiene limpo, medido); 23/23 na cópia.
