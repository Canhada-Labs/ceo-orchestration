**P1 — Cleanup can delete another writer’s replacement file.**

**FILE:LINE:** `CHANGELOG.md:103–104` (added release claim); `.claude/plans/PLAN-192/repass-rc1/CONDITIONS-rc1.md:94`; implementation `.claude/scripts/ceo-launches.py:149`, `:151`.

After a handled write failure, cleanup checks the destination with `lstat`, then separately calls `unlink`. Another process can atomically replace the destination between those operations. Cleanup then deletes that replacement, contradicting “only the inode this call created” and “never a file that is not its own.”

A read-only, in-memory interleaving probe reproduced this: the CLI created inode 101, observed it during cleanup, then deleted replacement inode 202 while reporting “the partial file was removed.” A control replacing the file **before** `lstat` correctly preserved it.

This requires neither symlinks nor deliberate ledger tampering: an ordinary concurrent writer to the user-selected `--out` path suffices. Condition 9’s state-tampering exclusion does not cover it. Round one’s disclosed interruption and failed-unlink cases do not declare this deletion race.

**Minimal fix:** Complete and close an exclusive temporary file before publishing through a no-replace operation; never unlink the public destination during failure cleanup. If deferred, explicitly disclose the replacement-deletion race in condition 14 and the CHANGELOG.
