# Inventário — features da API Claude vs. adoção em `ceo-orchestration`

Data: 2026-09-02. Autor: agente `study-api` (Staff Backend Engineer, skill `public-api-design`),
sob a skill `claude-api` (bundle 2.1.258).

## Escopo e método

`ceo-orchestration` roda **sobre** o Claude Code como harness (CLI) — não é uma
aplicação que chama a API Claude diretamente para servir usuários. O repo é
`stdlib`-only por contrato (`CLAUDE.md` §4); a dependência `anthropic` é
**opcional**, restrita ao "live adapter path" (`docs/stdlib-exceptions.md`,
`SBOM.md:56,161`) usado por `run-skill-benchmark.py` e pelos hooks de
`_lib/adapters/live/`. Isso significa que a maior parte da adoção de features
da API não aparece como chamadas de produção-para-usuário, e sim como (a)
código opcional de benchmark/replay atrás de `CEO_LIVE_CLAUDE=1`, (b) conceitos
do harness (Claude Code) que espelham conceitos da API (cache, thinking,
effort), e (c) decisões DOCUMENTADAS de não-adoção (`docs/MANAGED-AGENTS.md`
é "DOC-ONLY").

Toda afirmação sobre a API cita a seção da skill `claude-api` (SKILL.md ou
`shared/*.md`); toda afirmação sobre o repo cita `path:linha`.

## (a) 5 lacunas com maior razão valor/custo para este repo

1. **Refusal fallback (`fallbacks:"default"`) no adapter opcional.** Custo de implementação é baixo (um parâmetro + um beta header no `claude.py` já existente, que já faz parsing correto de `stop_reason:"refusal"` em `.claude/hooks/_lib/adapters/live/claude.py:957`) e o valor é direto: night-runs autônomas sob Fable 5.1 ganhariam continuidade automática sem depender do `fallbackModel` do harness (que resolve indisponibilidade, não recusa). Hoje o repo só *observa* a recusa (`model_refusal_observed`) — não se recupera dela.
2. **Advisor tool para o caso legítimo já identificado (custo, não VETO).** `docs/SOTA-GAP-MAP.md:70,92` já nomeia isso como a "marquee cost-quality lever" não testada. A ressalva de governança (`docs/HONEST-LIMITATIONS.md:112`) permanece correta — advisor nunca substitui VETO — mas isso não bloqueia usá-lo em staff advisory (qa/perf/finops) onde o repo já não exige VETO. Ação de baixo custo: testar se a chave de API tem a beta habilitada.
3. **Effort por mensagem (`mid-conversation-output-config-2026-07-01`) no `model_routing.py`.** O repo já mede empiricamente o custo de invalidar cache de prompt (PLAN-179, "F ≈ 97k tokens" de re-pay medido em produção, `CLAUDE.md` §5) — trocar effort hoje é top-level e paga esse re-pay toda vez. A troca para o padrão `role:"system"` + `content:[]` evita exatamente o custo que o próprio repo já quantificou.
4. **Cache 1h TTL no adapter opcional.** O framework já modela o multiplicador de cache-read por modelo em `budget-summary.py`, mas o adapter só grava `cache_control` de 5min. Para o padrão de night-run (gaps de dezenas de minutos entre turnos de um agente longo) o TTL de 1h — ou, no caso específico de Fable 5.1, um keep-alive `max_tokens:0` (mais barato que 1h dado o cache-read a 0,025×, `shared/prompt-caching.md` linha 156) — é diretamente aplicável e a economia é mecânica, não experimental.
5. **`thinking.display:"updates"` em vez do header `interleaved-thinking-2025-05-14` datado.** Dois ganhos no mesmo diff: remove um header de prompt-audit (GA desde 4.6) e adiciona visibilidade de progresso em turnos longos sem expor chain-of-thought bruta — relevante justamente para as sessões noturnas autônomas que este repo já roda.

## (b) O que NÃO se aplica ao Claude Code como harness (só API direta / Agent SDK / Managed Agents)

- **Managed Agents inteiro (Agent/Session/Environment/Vaults/Files/Outcome)** — `docs/MANAGED-AGENTS.md` já formaliza isso: o perímetro de governança local (hooks Pre/PostToolUse, sentinel de canonical-edit, HMAC audit chain) não atravessa a fronteira de um container hospedado pela Anthropic. Qualquer adoção exigiria o padrão "custom-tools-as-local-gate" (linha 86-122) ainda não implementado.
- **Claude Agent SDK** (`claude-agent-sdk`) — é um produto DIFERENTE (Claude Code empacotado como biblioteca para quem hospeda o próprio harness). Este repo já roda dentro do Claude Code nativo; não há razão para reimplementar o harness via SDK.
- **Fast mode, task budgets, tool search, structured outputs, context editing, Batches, cache** — todos aplicáveis apenas ao adapter opcional (`CEO_LIVE_CLAUDE=1`), nunca ao fluxo default do CEO/subagentes nativos, que passam pelo Claude Code e não fazem chamadas HTTP diretas à API Messages.
- **Advisor tool como server tool (`advisor_20260301` na Messages API)** — só faria sentido dentro do adapter opcional; o padrão real de pareamento "executor barato + verificador forte" que o CEO já usa é o **pair-rail cross-vendor** (Claude autor + Codex revisor), que é uma arquitetura de PROCESSO (dois processos, dois vendors), não um parâmetro de uma única chamada de API.

## (c) Impacto no pair-rail e no `/council` se algo acima for adotado

O pair-rail (Claude autor + Codex revisor) e o `/council` (Claude/Codex/Grok) existem precisamente para cobrir a lacuna que o advisor tool **não pode** cobrir: revisão cross-vendor genuína (`docs/HONEST-LIMITATIONS.md:112-121`, "Same-vendor reviewer caveat" em `CLAUDE.md` §5). Adotar o advisor tool para o caso legítimo (item a.2) não mudaria essa arquitetura — ele ficaria estritamente abaixo do pair-rail na hierarquia de evidência, útil só como triagem barata antes de gastar uma rodada de rail real, nunca como substituto. Adotar `fallbacks` (item a.1) ou `thinking.display:"updates"` (item a.5) é ortogonal ao rail: afeta apenas a resiliência/observabilidade do adapter opcional, sem tocar o mecanismo de dois processos independentes que dá ao pair-rail seu valor. A única mudança que tocaria o rail diretamente seria adotar Managed Agents multiagent como substrato de execução dos revisores — e isso está fora de escopo justamente pela quebra de FILE ASSIGNMENT já documentada em `docs/MANAGED-AGENTS.md`.
